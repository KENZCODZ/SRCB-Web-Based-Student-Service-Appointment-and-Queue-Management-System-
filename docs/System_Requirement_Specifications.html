1. Introduction

1.1 Purpose

This document specifies the comprehensive functional and non-functional requirements for the EduQueue: Web-Based Student Service Appointment and Queue Management System. The primary objective of this SRS is to establish a rigorous, formal specification of the software solution developed for St. Rita's College of Balingasag (SRCB). It serves as the definitive reference agreement between the system developers, academic evaluators, institutional administrators, department heads (Registrar, Dean's Office, Guidance Office, Finance/Cashier, IT Helpdesk, and Library), and the student body.

The system replaces manual paper logs, congested physical walk-in queues, and fragmented scheduling with a centralized, full-stack digital platform featuring real-time walk-in sequence ticketing, conflict-free appointment slot booking, role-based staff desk calling terminals, a lobby display monitor, and automated transactional email notifications.

1.2 Project Scope

The EduQueue system is an enterprise-grade, full-stack web application architected with a React 18 + TypeScript + Vite frontend, a native PHP 8.2+ RESTful API backend adhering to the MVC and Service Layer architecture, and a normalized MySQL 8.0 relational database.

The scope encompasses:

  • Student Self-Service Portal: Self-registration, JWT credential authentication, interactive service catalog discovery, conflict-free time slot appointment scheduling, on-demand walk-in queue ticketing, personal real-time position tracking, in-app notification center, and profile management.
  • Staff Operations & Counter Desk Terminal: Calling next student, starting service, completing transactions, skipping no-shows, and processing appointment dispositions (Approval with email voucher, Decline with reason, and Reschedule with revised date/time).
  • Public Lobby Live Display Monitor (/display): Fullscreen lobby kiosk display featuring live called tickets per counter desk, active ticket callouts, real-time digital clock, and upcoming waiting lists with auto-refresh polling.
  • Administrative Management Panel: Operational KPI overview, 7-day volume analytics, service & operating hours configuration, user account provisioning, system audit logging, and transactional email dispatch logs.
  • Multi-Channel Transactional Email Engine: Seamless integration with Resend, Brevo, SendGrid, SMTP, and Log driver for automated delivery of appointment confirmations, cancellations, and reschedule advisories.

2. Overall Description

2.1 User Needs and Pain Points

  • Need 1: Eliminating Physical Queue Congestion: Virtual walk-in ticketing with automated sequence generation (FIN-001, REG-002) and real-time personal line tracking showing exact students ahead and estimated wait minutes.
  • Need 2: Conflict-Free Appointment Scheduling: Conflict-free slot engine calculating availability from weekly operating schedules, slot durations, and student-per-slot capacity limits.
  • Need 3: Real-Time Transparency for Staff and Campus Lobby: Synchronized Public Lobby Display (/display) for campus TV monitors paired with visual callouts and audio alerts.
  • Need 4: Automated Verification & Communication: Automated transactional HTML email dispatch (Resend, Brevo, SendGrid, SMTP) delivering vouchers, reschedule dates, or cancellation reasons.
  • Need 5: Centralized Institutional Auditing & Capacity Control: Centralized executive dashboard with real-time KPIs, 7-day throughput analytics, immutable security audit trails, and email delivery monitoring.

2.2 User Personas

Persona 1 – The College Student: "Juan Dela Cruz"

Demographics: 20 years old, 3rd Year BS Information Technology, Working Student.

Goals: Book Transcript of Records requests around his class timetable; join cashier queues virtually without missing lectures; receive SMS/email alerts when his ticket is called.

Frustrations: Long physical lines at the Registrar and Cashier offices; unclear document requirements resulting in repeated office visits; lack of real-time queue position tracking.

Persona 2 – The Department Staff: "Maria Santos"

Demographics: 34 years old, Administrative Staff, Registrar Office.

Goals: View daily student appointments in advance; call next walk-in ticket with one click; communicate appointment approvals, reschedules, or rejections with automated email receipts.

Frustrations: Disorganized physical crowds around her counter window; manual logbooks and paper clearance forms; handling frustrated students who missed their turn.

Persona 3 – The System Administrator & Dean: "Dr. Ernesto Ramos"

Demographics: 48 years old, Dean / Academic Administrator.

Goals: Configure office operating hours and daily capacity thresholds; provision staff accounts; inspect system-wide audit logs and email delivery metrics; evaluate peak hour traffic analytics.

Frustrations: Absence of centralized operational reports; inability to restrict daily service volume to prevent staff burnout; unorganized student clearance tracking.

2.3 Assumptions and Dependencies

  • Users have access to modern web browsers (Chrome, Firefox, Safari, Edge) with JavaScript enabled.
  • The application is a full-stack system comprising a React frontend (Vite + TypeScript) and native PHP REST API backend connected to MySQL 8.0.
  • Stateless authentication is enforced via JWT (HMAC-SHA256). Public lobby screens (/display) do not require authentication.
  • Transactional email delivery utilizes configured mail API keys (Resend, Brevo, SendGrid) or SMTP fallback, with automatic fail-safe logging into the MySQL database.

3. System Features and Functional Requirements

3.1 Authentication, Authorization & Identity Management

  • FR1 The system shall provide a registration form allowing students to register with Student ID Number, First Name, Last Name, Email, Password, Contact Number, Degree Program / Course, and Year Level.
  • FR2 The system shall enforce client-side and server-side validation ensuring Student ID Numbers and Email addresses are unique within the database.
  • FR3 The system shall hash user passwords using standard PASSWORD_BCRYPT with cost factor 10.
  • FR4 The system shall authenticate users via Email or Student ID Number along with Password, issuing an HMAC-SHA256 JWT upon successful verification.
  • FR5 The system shall enforce Role-Based Access Control (RBAC) redirecting students to /dashboard, staff to /admin/appointments, and administrators to /admin/dashboard.
  • FR6 The system shall provide quick one-click demo login buttons on the login screen for rapid evaluative testing of Admin, Staff, and Student roles.
  • FR7 The system shall allow authenticated users to update personal profile details and academic program information.
  • FR8 The system shall allow authenticated users to change their password upon verifying their current active password.
  • FR9 The system shall provide secure session termination, invalidating client tokens and recording the logout in audit logs.

3.2 Institutional Service Catalog & Requirements

  • FR10 The system shall display an institutional service catalog categorized by office (Registrar, Dean's Office, Guidance, Finance/Cashier, IT Helpdesk, Library).
  • FR11 Each service card shall indicate its service classification (appointment vs queue), office counter location, estimated duration in minutes, daily capacity, and required prerequisite documents.
  • FR12 The system shall provide dynamic search and category filtering allowing students to filter services instantly without reloading the page.
  • FR13 Clicking an appointment-based service shall launch the Appointment Booking modal; clicking a walk-in queue service shall launch the Join Queue modal.

3.3 Appointment Booking, Slot Engine & Conflict Management

  • FR14 The system shall compute and display real-time available appointment time slots for any selected date based on service operating schedules, slot duration, and maximum student limits per slot.
  • FR15 The slot computation engine shall automatically deduct existing active bookings (pending, approved, rescheduled) to prevent overbooking.
  • FR16 The system shall prevent students from booking past dates or non-operating days.
  • FR17 The system shall prevent students from holding more than one active appointment for the same service on the same date.
  • FR18 The system shall assign a unique tracking code (e.g., APT-20261019-XXXX) to each confirmed appointment.
  • FR19 The system shall provide a "My Appointments" portal where students can view their bookings filtered by status.
  • FR20 The system shall allow students to cancel pending or approved appointments, immediately freeing up the reserved time slot.

3.4 Walk-in Queue Ticketing & Real-Time Position Tracking

  • FR21 The system shall allow registered students to join an active queue-based service with a single click.
  • FR22 The system shall automatically generate sequential daily queue ticket numbers formatted with service code prefixes (e.g., FIN-001, REG-002, IT-003).
  • FR23 The system shall restrict a student to one active queue ticket per service at any given time to prevent queue hoarding.
  • FR24 The system shall reject new queue admissions once a service reaches its configured max_daily_capacity.
  • FR25 The system shall calculate the student's real-time queue position (ahead_in_line) and estimated remaining wait time.
  • FR26 The system shall provide a visual status badge (waiting, calling, serving, completed, skipped, cancelled) updating via 5-second polling.
  • FR27 The system shall allow students to cancel their active queue tickets.

3.5 In-App Notification Center & Alerts

  • FR28 The system shall maintain an in-app notification center accessible via the header navigation bell.
  • FR29 The system shall display an unread notification count badge updating via background polling.
  • FR30 The system shall generate automatic notifications for appointment bookings, approvals, reschedules, and queue calling events.
  • FR31 The system shall allow users to mark individual notifications as read or mark all notifications as read in a single action.

3.6 Staff Appointment Workbench & Transactional Email Dispatch

  • FR32 The system shall provide staff with an Appointment Management workbench filtered by service, status, date, and student query.
  • FR33 Staff shall be able to Approve pending appointments, transitioning status to approved and triggering an automated HTML email voucher to the student.
  • FR34 Staff shall be able to Decline appointments with mandatory reason input, dispatching an official cancellation advisory email.
  • FR35 Staff shall be able to Reschedule appointments with revised date, start/end time, and staff notes, notifying the student via email.
  • FR36 The system shall log every email dispatch attempt into the email_logs database table.
  • FR37 The system shall enforce fail-safe email handling: an email failure shall never break or roll back primary database transactions.

3.7 Staff Queue Counter Desk Terminal

  • FR38 The system shall provide counter staff with an operational calling interface for their assigned service counter window.
  • FR39 The system shall provide a "Call Next Student" action that selects the oldest waiting ticket, marks it as calling, assigns the staff counter window, and broadcasts to the public display.
  • FR40 The system shall allow staff to transition ticket states to "Start Serving" (serving) upon student arrival at the counter.
  • FR41 The system shall allow staff to finalize transactions by clicking "Complete" (completed) or mark no-shows with "Skip" (skipped).
  • FR42 The system shall track timestamps for called_at, served_at, and completed_at to compute accurate service turnaround analytics.

3.8 Public Lobby Live Display Monitor (/display)

  • FR43 The system shall provide a dedicated public route at /display accessible without user authentication.
  • FR44 The display shall render high-contrast visual cards for every active counter desk indicating the service name, counter window, and currently called ticket number.
  • FR45 The display shall provide animated visual callouts and audio chime alerts whenever a new ticket is called.
  • FR46 The display shall feature an upcoming waiting list ticker summarizing waiting student counts and next-in-line tickets per department.
  • FR47 The display shall render a live institutional digital clock and SRCB branding.
  • FR48 The display shall automatically synchronize data via 5-second interval polling.

3.9 Administrator Control Panel, Services & Audit Logs

  • FR49 The dashboard shall display live summary KPI cards: Total Appointments Today, Active Walk-In Queue Count, Completed Services, and Total Registered Users.
  • FR50 The dashboard shall render a 7-Day Throughput Bar Chart comparing appointment volume against walk-in queue transactions.
  • FR51 The dashboard shall display service utilization by department.
  • FR52 The dashboard shall display an interactive live feed of recent system activities.
  • FR53 The system shall allow administrators to create, edit, and toggle active/inactive status for services.
  • FR54 The system shall allow administrators to configure recurring weekly operating schedules with custom slot durations and capacity limits per time slot.
  • FR55 The system shall allow administrators to provision new Staff or Administrator accounts directly with assigned departments.
  • FR56 The system shall allow administrators to toggle user account status (active / disabled).
  • FR57 The system shall log all critical actions into an immutable audit_logs database table with user ID, action tag, entity type, IP address, and JSON metadata.
  • FR58 The system shall provide an audit log search and inspection interface.
  • FR59 The system shall provide a dedicated email dispatch monitor detailing every outbound notification and delivery status.
  • FR60 The system shall allow inspecting email delivery payloads and error details.

4. Non-Functional Requirements (HCI Focus)

4.1 Usability

  • NF1 A user shall be able to reach any major functional section within a maximum of 3 clicks from the main navigation menu.
  • NF2 The primary task of discovering a service, selecting an available time slot, entering purpose, and submitting an appointment booking shall be completable in under 60 seconds.
  • NF3 All interactive forms shall provide clear, real-time inline validation with descriptive error feedback before network dispatch.
  • NF4 The interface shall utilize a polished institutional color palette (SRCB Navy #1E3A8A, Royal Blue #2563EB, Emerald Green #10B981, Amber #F59E0B) with consistent typography and micro-animations.
  • NF5 All operational adjustments shall be performed entirely through graphical UI modals without requiring manual SQL.

4.2 Performance

  • NF6 Backend REST API endpoints shall execute and respond within 200 milliseconds under standard institutional network loads.
  • NF7 Initial page loads shall render within 1.5 seconds on modern desktop browsers and under 3 seconds on 4G mobile connections.
  • NF8 All frequently queried columns (user_id, service_id, appointment_date, queue_date, status) shall be indexed in MySQL for sub-10ms query execution.
  • NF9 Live queue trackers and notification centers shall utilize lightweight, debounced REST polling (5-second intervals).

4.3 Accessibility

  • NF10 The application shall adhere to WCAG 2.1 Level AA accessibility criteria across all screens.
  • NF11 All body typography, headings, buttons, and alert badges shall maintain a minimum color contrast ratio of 4.5:1 against their backgrounds.
  • NF12 All interactive elements shall be fully navigable and actionable using only keyboard inputs (Tab, Shift+Tab, Enter, Space, Escape).
  • NF13 All custom dialogs and icons shall incorporate appropriate ARIA attributes for screen reader compatibility.

4.4 Compatibility & Responsiveness

  • NF14 The web application shall render identically on latest versions of Chrome, Firefox, Safari, Edge, and mobile browser variants.
  • NF15 The UI shall dynamically adapt across viewports from 320px (mobile) to 1920px+ (large monitor / Lobby TV Kiosk) using Tailwind CSS responsive utility classes.
  • NF16 All buttons and interactive controls shall provide minimum touch target dimensions of 44x44 pixels for touchscreen mobile navigation.

4.5 Security

  • NF17 All database interactions shall strictly utilize PDO prepared statements with parameterized inputs. Emulated prepared statements shall be disabled.
  • NF18 All user credentials shall be secured using standard PASSWORD_BCRYPT with cost factor 10.
  • NF19 All private API routes shall validate incoming HMAC-SHA256 JWT tokens with standard 24-hour expiration claims.
  • NF20 Administrative and staff endpoints shall be guarded on the server side by RoleMiddleware.
  • NF21 All incoming request payloads shall be sanitized and escaped upon output formatting.
  • NF22 The backend API shall enforce explicit CORS origin headers and secure HTTP headers.
  • NF23 All secrets (database passwords, JWT keys, mail API credentials) shall reside exclusively in server-side .env files.

4.6 Maintainability & Architecture

  • NF24 The backend codebase shall strictly enforce separation of concerns across Core/, Middleware/, Controllers/, and Services/ layers.
  • NF25 The frontend application shall channel all network interactions through a centralized typed API service module (src/services/api.ts).
  • NF26 External email dispatch failures shall be captured gracefully and logged in email_logs without rolling back primary appointment or queue database transactions.
